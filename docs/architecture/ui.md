## Composition and Boundaries

[main.dart](../../lib/main.dart) initializes Flutter and composes the application, theme, initial route, store, signaling factory, tab coordinator, and ICE configuration. The current root widget is named `MyTreeDemoApp`; the name is retained even though the production screen is the family-tree editor.

[RoomPage](../../lib/ui/room_page.dart) owns room/menu navigation and the lifetime of one `RoomSession`. It does not implement field merging, storage formats, or transport protocols. [TreeEditor](../../lib/ui/tree_editor.dart) owns tree presentation state, and [PersonBiography](../../lib/ui/person_biography.dart) owns biography forms and media input. [person_family_history.dart](../../lib/ui/person_family_history.dart) owns the surname/marriage panel and its draft/edit/delete dialogs, plus the source-choice and new-person fields shared with Add Relative. [tree_search.dart](../../lib/ui/tree_search.dart) groups person matching and the compact `TreePersonSearch` overlay widget; it depends on the tree model, not the canvas, forms, or session. [room_dialogs.dart](../../lib/ui/room_dialogs.dart) groups related admission, participant, invitation, settings, and journal dialogs. [patronymic_dictionary_dialog.dart](../../lib/ui/patronymic_dictionary_dialog.dart) owns the room dictionary's read/edit forms; generation and dictionary projection stay in the tree model.

Dependencies are explicit enough for widget tests to use memory stores/fake signaling. The optional `roomEditorBuilder` is a test seam for preserving historical room-lifecycle tests; the production default is `TreeEditor` with `requireFamilyTree: true`. It is not a hidden alternative text-demo screen offered to users.

## Room Navigation and Visible State

The entry point consumes and removes the browser's initial fragment before starting Flutter, retaining the original URI only for invitation parsing; its root route is named `/` so navigation cannot reannounce a room ID. `RoomPage` restores the client ID and last room without writing an invitation back into the address, handles the captured initial invitation, offers an optional participant alias when none is saved, and creates/replaces the session. Accepting `''` proceeds anonymously; canceling returns without creation/admission, and restoring a saved empty alias does not prompt again. Generation/mounted checks prevent an older asynchronous open from replacing the current room.

The body selects one of three surfaces:

1. Menu: create/join and local-data errors.
2. Entry/loading: the current synchronization status, truthful failures, retry, and an explicit accepted local-copy option where permitted.
3. Room: storage/local-copy warnings plus the tree editor, only after the joined session has initial synchronization or an explicit local-copy bypass.

`initialSyncComplete` represents the applicable verified entry path: durable peer exchange, separately validated/persisted Disk admission, or explicit new-room solo initialization. Disk entry reports **История загружена с Диска · онлайн-сверка продолжается**; it does not manufacture peer ACK/cohort/local-tab protocol evidence or guarantee the newest global copy. `localCopyOpened` remains an explicit unsynchronized display bypass, not admission. Neither a recent-host hint, a legacy latest-text preview, nor an open channel bypasses the gate. Saving errors are never hidden by normal navigation. Room switches and menu exit wait for `flush()` before disposing the session; a failed flush keeps the room/error visible. Immediate optimistic display or invocation of the append API is not confirmation that storage has acquired its asynchronous journal lock. Closing a tab is not a supported save path.

A transient initial DataChannel close keeps loading/reconnection within the original verification deadline instead of immediately switching to a terminal screen. If that deadline expires, Retry and the accepted-local-copy option remain available; background reconnection can still remove the failure only after a complete durable exchange. The UI never opens a local copy automatically or treats a reconnect as confirmed history. Specific capability, integrity, and saving errors retain precedence over generic transport status.

A qualifying return from suspension invalidates an already-confirmed copy's readiness and shows **Сверяем изменения после возвращения…** until a fresh durable peer exchange or validated/persisted Disk read completes. The resumed attempt cannot infer success from solo discovery or old checkpoint flags. An opaque, input-blocking overlay also covers a phone biography or dialog above the room page without destroying that route's draft. Timeout/errors retain the ordinary retry and explicit unconfirmed-local-copy escape. Healthy focus changes, including long Alt+Tab switches while execution/traffic continues, and an already-open explicit local copy do not reset the gate. A genuine execution gap or lost/silent last peer still requires fresh verification; elapsed hidden time or absent signaling for a Disk-only copy alone does not.

The AppBar exposes the room-title menu and participant button. The menu's last row is selectable build-version text (`MYTREE_BUILD_VERSION`), implemented as a non-action `PopupMenuEntry` rather than a disabled `PopupMenuItem`. This retains read-only text-field semantics, focus and keyboard copy without exposing a navigation action or authoring history. Pages builds stamp UTC date/time once at compilation (`yyyy.MM.dd-HHmmss UTC`), so reload and the viewer's clock cannot change the installed version. Unstamped development builds show `dev`. The participant button distinguishes other-online count from unavailable connectivity. Roster grouping and effective roles belong to `RoomSession`; the dialog handles centered editor-first presentation, badges, and promotion confirmation. Guest avatars have an opaque wood-brown (`#875826`) eye badge with a contrasting white glyph in both themes, separate from the green online dot. Participant tiles are 96 px wide with a one-line 80 px name area and ellipsis. A `TextPainter` using the actual style and text scale detects truncation: a truncated label gets its complete displayed alias/fallback in the tooltip. An active bound person's durable birth name in the current local name mode is always included, even when a short explicit alias fits; equal alias/name text is not repeated. Participant aliases themselves are not reformatted. Short unbound labels have no tooltip.

**Change My Name** uses the same optional-alias dialog and can persist an explicit blank to clear the old alias. It shows only the name input, optional **Отменить «Это я»** (Release This Is Me) action, and save/cancel controls, without explanatory paragraphs or a static bound-person caption. The input hints **Аноним**; the release action's tooltip can identify the bound name in the current local name mode. Validation and saving failures remain visible when relevant. Release awaits the session's durable operation, blocks dismissal while busy, and reports failures in the dialog. Success removes the release action through the live session listener without closing the dialog or losing the typed alias draft. It changes only the own actor's claim, not people or other grouped actors. Guests can edit/clear their own alias but receive no release action.

## Invitations and Disk Entry

`RoomPage` passes the strictly parsed invitation role and optional `RoomDiskAccess` from the captured initial fragment or pasted invitation/code into `RoomSession`; malformed access is an invalid invitation, never a fallback to a raw ID. An editor invitation can durably promote the same already-accepted guest actor. Clean saved-room restore, plain IDs and guest invitations retain the guest role; an editor is never demoted by those paths. The entry form distinguishes plain-ID admission, which still needs an online participant, from a Disk-enabled invitation, which can enter without one while Disk is reachable. Session admission owns bounded history/owner-role validation and the ordering of history/profile/access persistence **before membership**. The page does not invent membership or accept an empty tree when a cloud read fails. Failures stay visible with retry/ordinary online admission; an already accepted local copy remains a separate explicit choice.

`InviteParticipantsDialog` keeps the existing guest/editor selection and permission guards. For an active Disk binding, editors and guests retaining matching public access use `prepareDiskInvitation()` for Copy URL, Copy Code, and Show QR, rather than constructing an access-bearing invitation during build. A guest without public access keeps ordinary ID/URL/QR invitations, which still require an online participant for first entry:

- Editor sharing asks **Передать доступ редактору?**, explaining that the invitation contains the application-folder key and is only for trusted editors. Canceling does not load/copy that access. Consent is retained only for subsequent actions in the same dialog.
- Guest preparation first reuses valid public access. If none exists, an eligible explicit editor can confirm **Разрешить гостям доступ к Диску?**. The confirmation says the tree's history, **including deleted records**, becomes readable and that other trees are not published. Session preparation publishes only the active binding folder after confirming its current durable copy. A guest may forward existing public access but cannot publish a folder or receive an editor token.
- Access preparation blocks duplicate commands, role changes, cancellation, and dismissal until it completes; mounted/role/binding/credential checks protect asynchronous completion. Missing/mismatched access or a preparation failure produces a safe error, not a misleading plain invitation.

The full access-bearing URL/token is not rendered as selectable dialog text. The displayed ID remains available, but with Disk access **Скопировать код** copies a complete nested JSON invitation; without Disk it retains **Скопировать ID** and guest-only raw-ID behavior. Web URL/QR data carries optional `disk` only in the fragment; native QR uses nested JSON. Oversized QR data gives a safe URL-copy fallback, and clipboard errors never interpolate or redisplay the token. Sharing the resulting clipboard/QR contents is deliberate bearer access, not encryption.

A guest admitted through public access retains a separate local public pointer and receives read-only periodic/resume Disk updates. It has no private API/upload/manual-sync controls; “history read from Disk” does not acknowledge the guest's own local metadata to the cloud. Peers can still exchange that metadata through ordinary room synchronization. Disk-read status/errors are distinct from local saving, participant connectivity, and an editor's confirmed cloud copy.

## Room Settings and Disk Status

`RoomSettingsDialog` combines the existing room-name form with a [Yandex Disk section](yandex-disk.md). An unbound editor initially sees **Подключить Яндекс Диск**; only expanding it adds the obscured **OAuth-токен** input, with suggestions/autocorrect disabled. Ordinary settings still contain one text field. There is no configured OAuth client ID or browser login flow: token issuance happens externally. Before calling connect, a brief confirmation discloses that application-folder access is shared with room editors, not guests. The controller is cleared after successful connection.

Binding, role, status, and error presentation listen to the live session. Editors can manually synchronize an active binding; only an eligible owner sees unlink. **Отвязать Яндекс Диск?** confirms **Файлы на Диске сохранятся.** It does not promise OAuth revocation or deletion. Guests see status without token/connect/sync/unlink controls. Disk failures are separate from the room-name field's error; raw credential-bearing exceptions are never interpolated. Pending user commands disable fields, other commands, cancel, and dismissal; permissions and the captured binding identity are rechecked after confirmation. Background cloud polling is different: it disables duplicate manual sync but must not trap the user in settings or prevent rename/close.

For every joined participant, the main page represents Disk status with `RoomDiskStatusButton`, a cloud icon immediately left of the participants action on both narrow and wide screens; there is no separate Disk status row above the editor. For guests it is a disabled, read-only status control with a tooltip (long-press on touch) and accessible label, never a connect/upload/manual-sync action. Their read status remains distinct from a confirmed editor copy. The theme-colored overlay is a green `primary` check only for the acknowledged current durable set with no pending retirement/error, neutral `onSurfaceVariant` sync arrows for busy/queued/waiting states, or an `error`-colored cross for failures. A running command keeps neutral arrows and disables duplicate taps. The tooltip and single accessible button label retain the complete status and sanitized error, including an unfinished prior unlink when an active copy is already confirmed. For an active binding or pending unlink, pressing the cloud invokes existing manual synchronization directly, not settings; unexpected command failures receive safe generic copy. Editors also see a neutral bare cloud when Disk is not connected, with the full `Не подключён` tooltip; pressing it opens Disk settings instead of attempting an impossible synchronization. Guests have no sync action. Participant/network connectivity does not gate a valid Disk attempt. Local-saving errors, local-copy warnings, WebRTC readiness, and participant connectivity remain separate and are not hidden by this compact presentation.

A locally saved detach can still be awaiting final cloud upload; a confirmed local save or online participant is not a confirmed Disk copy. An old binding's independent retirement can remain pending/failed while a new active binding shows its own status. Once no binding is active, replacement connection remains available; its success must not clear the old delivery/error or be presented as its acknowledgment.

## Patronymic Dictionary

The room menu places **Словарь отчеств** immediately below **Настройки комнаты**. Guests can read the combined built-in dictionary and room overrides; editors can add entries or edit either source. Each entry contains the father's given name and male/female patronymic forms, not an editable patronymic on a person. Reset removes only that room override and restores the built-in entry or algorithmic fallback. Session commands persist dictionary changes through the ordinary tree history; dependent names and search results refresh from the live projection. Pending writes block dismissal and duplicate submission. A failed optimistic save remains visible and Retry flushes the same immutable operation instead of creating another edit.

## Canvas State and Layout Consumption

`TreeEditor` keeps the selected main person, trunk mode, toolbar visibility, open desktop biography, outer scroll controller, and independent per-generation controllers locally. The initial person is the actor's existing durable binding, otherwise the existing `root`, otherwise the first active person by ID. Deleting the last person shows an empty state with an editor-only Add Person action; it does not resurrect the deleted root. These presentation choices are not shared operations.

Name format is also local, unpersisted UI state: default **ИФ** retains given-name/surname captions; **ФИО** renders surname/given-name/computed patronymic. `RoomPage` owns one `ValueNotifier<TreeNameMode>` and passes it through the optional `nameMode` argument. Standalone `TreeEditor` owns its fallback notifier and never disposes an injected one; `PersonBiography` also accepts that notifier with an ИФ fallback. The same notifier reaches the graphical picker, desktop biography panel, mobile biography route, binding confirmation, relative labels, and selected-relative dialog caption. Picker/toolbar changes therefore refresh open captions live without tree/history writes. Raw name/surname inputs, name-only canvas cards, album labels, and deletion copy are unchanged. Patronymics remain model-computed/read-only from the accepted father and child's sex; missing/unknown values add neither empty separators nor an edit field. Legacy name text stays opaque and is not split by the UI.

`TreeLayout` supplies signed cross-axis coordinates and absolute generation ranks. The widget adds viewport padding and projects them by orientation:

| Orientation | Generation progression / outer scroll | Independent generation scroll |
| --- | --- | --- |
| Portrait | Left to right / horizontal | Vertical |
| Landscape | Top to bottom / vertical | Horizontal |

The compact current-mode icon opens choices with icons and explanations. Every orientation uses one 45 px toolbar row (40 px controls, 2 px vertical insets, and a 1 px divider). That row sits directly under the room AppBar and spans its full width; the room body does not insert padding between them. From the left: collapse, mode, **Выровнять всё** (Align All), then the 108 px zoom group **[−] [+] [percentage]**. Minus/plus targets are 32 × 40 px; the percentage-only reset is 44 × 40 px, with no magnifier. A compact **ИФ / ФИО** name-format menu follows zoom; search stays at the right. On mobile it is a compact 64 × 36 px outlined magnifier field; focusing it hides all other controls and fills the toolbar's content width. Desktop search is fixed at 240 px and does not expand on focus. The compact/mobile criterion is view width below 900 px, independent of height or orientation; a wide but short desktop stays fixed-width, while exceptionally narrow views scale the left control strip down rather than add a row. The selected person's name is not repeated in the toolbar. These controls are shared by the existing-person picker. In the active canvas, **1** selects the paternal mode, **2** the maternal mode, **3** both modes, and **Space** invokes the existing Align All action. The same view-only shortcuts remain available with the toolbar collapsed and in the active picker. They do not override text entry/IME, modified-key combinations, focused button activation, or a covering dialog/route, and do not append journal operations.

On desktop platforms (Windows, macOS, Linux), toolbar tooltips include the existing **1/2/3** mode mappings, **Space** for Align All, and **Ctrl + wheel down/up** for zoom out/in. Android/iOS keep short labels even in a wide viewport; a narrow desktop retains keyboard hints. This platform distinction is independent of the width-based compact layout above. Controls without a shortcut (collapse and zoom reset) do not advertise one. The shared picker uses the same tooltips.

Collapsing removes the entire toolbar and its search overlay, reclaiming its height; only a floating reopen button remains over the canvas. Mode, selected person, and zoom are retained, while the unmounted search field's transient query is discarded. The minimum zoom derives from a nominal 4 mm outer avatar using the browser/reference conversion of 96 logical px per inch: `4 × 96 / 25.4 / 60`, rounded upward to a whole percentage, currently **26%** (a 15.6-logical-px avatar, about 4.13 nominal mm). Maximum zoom stays **200%**. This is the user-approved approximate browser-unit fallback: neither screen resolution nor device-pixel ratio supplies reliable physical DPI, so it is not a guarantee of 4 real millimeters and does not invent a display-size calibration. Buttons move to the next 10-percentage-point grid mark in their direction, clamped to the floor (30% → 26%, 26% → 30%); the percentage control resets to 100%. The sex legend has been removed. Orientation comes from the device view, while the biography sidebar decision uses the available width (900 px threshold, 360 px panel). The lower-right biography and picker-confirm actions are both 56 × 56 px with 28 px icons and remain unscaled.

Zoom is local presentation state, not a document operation or a shared/persisted setting. Only the canvas scene is scaled: nodes, text, blocks, curves, and the outer scrollbar share one logical coordinate system with a viewport equal to the physical canvas divided by zoom. A top-left overflow/transform wrapper preserves hit testing over the whole physical viewport, including when zoomed out. The toolbar, biography sidebar, and floating biography action remain unscaled. The graphical relative picker has its own independent zoom.

Ctrl+wheel zooms toward the pointer in absolute 5-percentage-point grid steps per 100 units of wheel travel, not multiplicative jumps. Small deltas accumulate; reversing direction, reaching either bound, or using another zoom control clears the residual so there is no overscroll debt or shifted grid. On web, Flutter encodes Ctrl+wheel or trackpad pinch as `PointerScaleEvent` with `exp(-deltaY / 200)`, even without a physical Ctrl key; the UI recovers that delta with the inverse logarithm. Native Ctrl+`PointerScrollEvent` follows the same path. Arbitrary pinch scales snap directionally to the next grid mark when wheel/buttons are used. Touchscreen pinching remains continuous: it tracks two contacts in an unscaled listener instead of competing with nested one-finger drag recognizers. It freezes both scroll axes while any pinch contact remains and suppresses node actions until all contacts lift. Ordinary one-finger dragging is then restored.

Before zooming, the UI captures the main coordinate and each generation's independent cross coordinate at the same focal point. It computes the required offsets in the new base geometry, then adds common leading/trailing cross padding to **every** generation so all offsets fit, including a singleton or a row already at either boundary. The main axis receives equivalent padding, with separate leading/trailing extents. Narrow scroll controller/position subclasses reconcile new offsets before painting: changed dimensions use the layout pass, while unchanged dimensions apply pixels and invalidate paint/semantics during input handling because that viewport may skip layout. Layout-time reconciliation itself never notifies listeners; a coalesced, disposal-guarded post-frame notification publishes corrected scroll offsets afterward. This is not a workaround for every Flutter web semantics issue: the recorded browser run found accessibility DOM bounds diverging from unchanged painted parent cards during a later ordinary outer drag. No individual generation clamps away part of the common zoom transform: all node rectangles follow the same focal affine transform and independently panned levels retain their relative alignment. Padding is local viewport state, not a layout operation; orientation/session changes reset it. Ordinary wheel deltas are converted back to logical units, preserving physical movement at every scale. Whole-canvas middle panning reuses this focal transform at the unchanged scale.

Selection or a trunk-mode change requests visibility-aware alignment. When selecting a fully visible card, its pre-selection screen position is the selected generation's anchor, even if canonical sibling/partner blocks move to other slots. This target anchor takes precedence over that row's packed-origin preservation; other generations retain ordinary row-origin/shared-card compensation. A selection clipped before the input explicitly requests centering of the selected card, even if canonical partner/block reordering makes it fully visible near an edge before deferred alignment runs. This one-shot intent belongs to that selection, not a global Align All request: already-visible relative rows keep normal visibility-aware behavior. A newer selection, zoom, or mode change replaces/cancels it, and explicit Align All still recenters. Pending anchors compose across rapid prepaint selections rather than reading stale painted geometry. An already-visible selection, relevant parents, and descendant generations containing a fully visible child keep their screen positions. Clipped required content is centered on the **viewport**, independently of the selected node's current screen position. In a single-line mode, ancestor candidates follow the preferred parent repeatedly at every step: mother → maternal grandmother → her mother, or the corresponding father chain. Only a missing preferred parent permits the other parent as fallback. They are not the whole maternal/paternal ancestry branch and are never averaged with that chain person's co-parent. Both-lines mode uses all direct ancestors on each level. Descendant candidates are actual descendant blocks. If a candidate span is too wide, the real card nearest that viewport's current center wins (person ID breaks equal-distance ties), rather than an empty gap. Main-axis alignment reveals and centers the selection and preferred parent together when they fit, otherwise the selection wins.

**Выровнять всё** forces the same centering even for already-visible content. Every generation participates: the selected generation targets the selected card, other generations use the relevant candidates above or all their nodes when none are relevant. It does not change mode, selection, zoom, history, or block order. Initial entry, orientation changes, and newly added parents request an initial alignment; ordinary network notifications and text edits do not reset user-chosen scrolling. User input can interrupt animations, and reduced-motion/accessibility settings suppress animated movement.

Every generation groups child blocks by either known parent, not merely the selected person's descendants or one mode-preferred parent. A shared-mother cohort still applies when the children have different fathers, and the symmetric shared-father rule also applies. Selecting a cousin or another relative is not permission to insert their block into a compatible cohort. Full-sibling blocks remain indivisible, with unchanged member sorting. Actual ancestral seams and the ancestor corridor can take precedence where genuinely incompatible; context-partner proximity and focus-only descendant convenience do not veto structural parent cohorts. Conflicting overlapping cohorts use deterministic compatible priorities rather than promising impossible simultaneous adjacencies.

Rebuilds use the canonical layout for the current document, selected person, mode, and metrics; previous selections cannot change block/node order. Modes may choose different block orders, but compatible shared-descendant branch constraints keep maternal blocks before paternal blocks in every mode, including ancestors whose connections are not currently painted. These constraints never reorder members inside a sibling block; only two-line ancestral parent-card adjacency can override their canonical chronology. In both-lines mode, actual ancestor blocks also form a contiguous corridor on each parental generation: intervening nonancestor blocks move outside that corridor, toward the maternal or paternal side of their nearest recorded path. Ambiguous/disconnected intruders use the nearer outer edge deterministically. Already-exterior context stays put unless a stronger structural common-parent cohort requires moving it; neutral exterior placement is not an extra hard constraint that can veto such a cohort. Whole sibling blocks, accepted ancestral card seams, generation ranks, and relationship targets are retained. Lower both-lines rows likewise keep blocks containing lineal descendants together, so nieces/nephews cannot interleave direct-child blocks. Ambiguous maternal/paternal context first follows an exclusive blood-relative side from the selected generation through real child edges; a sister's descendants therefore stay on that sister's side when unambiguous. Truly ambiguous/disconnected intruders use the nearer edge deterministically. These sides follow recorded parent roles, not node sex; a shared ancestor above a sibling pair alone does not override their birth order. View compensation compares the old and new cold row geometry. When block identities, membership sets, extents, and packing metrics are unchanged, it follows the actual packed row-origin translation, measured from the first packed edge even if a different block now occupies that slot. Required whole-block or within-block permutations are not scrolling. Virtual zero included in generation bounds is not used as a content edge. When membership or extents change, the shared-card fallback still prefers a stable sibling-block cohort for displacement ties. It must not anchor a whole generation to the first visible or most-numerous moving context cards when they are being reordered. Preservation offsets are staged through the existing view-scroll controllers and consumed during layout before paint; unchanged-size input paths apply them before rebuilding if the viewport would otherwise skip layout. Post-frame work no longer performs preservation jumps: it clears bookkeeping and handles intentional visibility/Align All adjustments only. This avoids a one-frame displaced row followed by a settled correction. Pure equal-sized parent swaps leave the generation's scroll offset and unaffected cards in place; common origin/padding changes are compensated without inheriting historical permutations. The selected person's main-axis position is retained separately. Actual structural constraints can still require card movement; see [layout stability](tree-layout.md#signed-packing-and-centering).

Wheel deltas retain their physical axes: vertical wheel motion scrolls vertically (the outer generation axis in landscape, the hovered generation in portrait); horizontal trackpad deltas scroll horizontally. Primary mouse dragging is enabled on the canvas, including horizontal generation rows, without turning a completed drag into a node tap. Holding the middle mouse button rigidly translates the **whole canvas** in both physical axes, preserving all independently chosen generation offsets. A single unscaled canvas listener owns that gesture, including presses in blank padding; it cancels existing scroll animations and accumulates motion arriving before the next frame. Common padding extends as needed so short/singleton generations or a scroll boundary cannot absorb part of the translation. Release, cancellation, or loss of the middle-button state stops the gesture without inertia or a node action. This updates viewport geometry, not the domain layout or journal. Separate listeners inside generations resolve ordinary wheel events before enclosing scrollables and clamp their controllers independently; the main scroll content has an equivalent wheel fallback for empty leading/trailing padding. Touch/trackpad gestures and the outer scrollbar remain available.

The canvas disables automatic scrollbars and has exactly one explicit outer `Scrollbar`, attached to the main controller and depth-zero notifications. Generation scrollables retain their independent controllers and gestures but have neither explicit nor automatic scrollbars. Each generation's `MouseRegion` spans its full cross-axis viewport, including empty space. Hover paints `onSurface` at alpha `.035` across that band; without hover its background is transparent. Hover is local presentation state and writes no operation.

Scrolling invalidates the connection painter through a small `Listenable`; it does not recalculate the domain layout on every scroll tick. Orientation changes rebuild viewport geometry and request a fresh alignment. One `Flex` changes direction without replacing the generation container, preserving keyed generation scroll views/controllers while a focused search survives rotation and desktop/mobile breakpoints. The connection painter must never see duplicate old/new attachments caused by swapping a `Row` for a `Column`. A separate real-browser limitation remains: with Flutter accessibility semantics enabled, rotation can detach/reinsert the route's semantics ancestor and blur the native input even while its query/caret and Flutter widget state survive. The toolbar then correctly leaves focused-search mode; it does not forcibly reacquire focus after a native blur. End padding lets edge nodes be centered rather than merely clamped to a screen edge.

## Tree Search

`searchTreePeople` matches every whitespace-separated query token as a substring across `fullNameWithPatronymic` and life years. Both the main tree and graphical picker always display **ФИО** in search labels and accessibility semantics, independently of the local ИФ/ФИО setting. Search therefore includes the automatically computed patronymic as well as the effective birth surname and opaque existing name text. It lowercases text and treats `ё` as `е`; token order is irrelevant. Legacy separate maiden records are not a second search name or caption. Search adds no name parser or editable patronymic field. Results use the same strict canonical order as sibling members and relative lists: **unknown birth dates first** (treated as older), then actual birth date ascending. Equal/missing dates compare the trimmed given-name field, ignoring case and treating `ё` as `е`, then person ID for a total tie. Surname changes, selection, and death years do not supply sorting keys.

`TreePersonSearch` takes the current immutable people map and an ID callback, with compact/back-button presentation and focus reporting for the toolbar. Its `OverlayPortal` keeps suggestions out of toolbar/canvas layout and bounds them to the viewport and software keyboard, opening upward when appropriate. Nonempty focused queries show matches or a no-results message. Arrow keys move the highlight and Enter/software search selects; active IME composition is not intercepted. A stable keyed search slot retains input, focus, and overlay state while mobile focus replaces the other toolbar controls. The back arrow, Escape, system back, outside tap, or blur restores the compact row without clearing the query; selecting a result clears it and restores the row. Desktop Escape dismisses suggestions without expanding/collapsing the field. Clearing closes suggestions, and Ctrl+wheel/pinch over the field or suggestions does not zoom the canvas.

Each build queries the live map rather than a cached document index. Remote additions, edits, and deletions update suggestions without replacing query/caret state; a callback rechecks that the ID still matches the current query. Selecting a result only browses to that ID through the editor's normal selection/alignment path. It never opens a biography, appends history, or confirms an existing-relative choice.

## Nodes and Connections

Normal sibling blocks use an olive wash at 24% opacity; cousin-style blocks use a visibly lighter 14% wash, while distant blocks retain neutral grey at 24%. A mixed block takes its strongest model emphasis, so an ancestor's normal wash wins over a cousin-style sibling in the same block. The UI uses 108 px cards with 60 px rounded-square avatars and 3 px sex-colored outlines. The selected card has a thinner 1.5 px outline in that same node's sex color and a 50%-opacity `surfaceContainerLowest` fill. Only that selection fill is translucent; names retain opaque backing so crossing links cannot obscure text. Names and outlines use brown for male, green for female, and neutral for unknown. Male/female avatars retain their corner symbols; unknown-sex avatars have no corner badge. An unnamed avatar can still show its central person fallback. Nodes have no hover tooltip; the accessible selection label and biography navigation remain. Cousins, nephews/nieces, full/half siblings of every direct ancestor, and stepparents (other co-parents or marriage partners of either direct parent) use the same desaturated cards and olive context blocks; actual ancestors remain normal. Stepparents' links to half-sibling blocks use the same muted curve treatment, while the actual shared parent's link remains normal. Distant cards are monochrome, including text and photos. Long names remain bounded and have opaque surface-colored backing.

Partners are inferred as the other recorded parents of the selected person's direct children. The editor caches that set with each document/selection rebuild and renders only those individual cards in normal full color, including photos and text. This color override does not promote layout emphasis, block wash, siblings, or connection policy. Separately, layout in every trunk mode brings the selected person's partners nearby first, then the partners of their full/half or explicitly linked siblings. When a direct parent has another partner, the parents/stepparents also request a compact whole-block group after those priorities, keeping compatible unrelated blocks outside rather than between their cards. Proximity moves whole sibling blocks without changing member order, generation ranks, or accepted structural parent cohorts. Siblings' partners receive no new full-color override, block wash, badge, or connection styling; the existing visual policy above is unchanged. Only actual parental adjacencies in the selected person's ancestry may reorder members, exclusively in two-line mode and at every ancestral level, as described in [tree layout](tree-layout.md#compatible-parent-adjacency-and-focus-refinements). Selection, unlinking, and person deletion recompute partners from current projected relationships; no spouse field or view-only operation is persisted.

A nonempty `surnameForBlock` result is a centered, single-line ellipsized footer in `onSurface` at alpha `.50`. It uses effective surname configurations: a singleton's sex-specific form, an agreed multi-person plural, or `разные фамилии` for mixed values. The 20 logical px footer starts 2 px below the block background, outside its wash. Background dimensions are identical with and without a surname; no surname means no footer. Cards and their packing/connection geometry stay unchanged; surname rendering does not add ranks or alter block identity. See [surname semantics](tree-model.md#canonical-surnames).

The canvas groups connections by child block instead of drawing a line to every sibling. Both real parental connections are retained for the selected person and ancestors in any mode. Full/half sibling blocks also retain both known parents, including a maternal half sibling's separate father or a paternal half sibling's separate mother, independently of trunk mode. Immediate child blocks show both co-parents too. Focus/ancestral blocks keep their relevant avatar endpoint; separate sibling and child blocks use the whole-block center. Other deeper descendant/neighbor blocks receive one relevant connection; distant target blocks receive none. Connection identity, ancestral avatar target, and paint order do not depend on trunk mode: the mode controls packing and alignment, not which relationship is shown. An ancestral block targets the selected person when present, otherwise its first direct ancestor in canonical person order (unknown birth first, date, normalized given name, then ID). This target order is independent of the displayed sibling order, which two-line parent adjacency may override. A one-edge context block prefers a selected ancestor, then a direct descendant, then another blood relative, and finally the first parent by that same canonical order. Blood-relative membership follows real parent links upward from the selection, then real child links and active direct sibling edges from that ancestor closure; it never crosses upward through an unrelated co-parent. This also keeps a parentless explicit sibling's child on the related branch. Direct sibling edges themselves are not parent curves. Thus a niece/nephew or cousin follows the related parent rather than an unrelated partner merely because of their birth date/name. If both candidate parents qualify at the same priority, canonical order breaks the tie. These are rendering choices among actual stored parent edges, not new relationships. The connection builder has no mode parameter or mode-dependent trunk-ID input; all edges are sorted by child block, target, and parent ID before painting.

Cubic curves start at the parent's avatar edge. Selected/ancestral targets use the relevant person's avatar edge; descendant/neighbor targets use the center of the entire sibling block's facing edge, not the oldest child's avatar. Connections use brighter brown (`#AE742C`), green (`#338B64`), and neutral (`#8A9087`) hues at 60% opacity. Cousin-style links, including nephews/nieces and ancestral siblings, blend toward neutral and use 40% opacity when the source node or target block has cousin emphasis, visibly muting them without hiding them. The painter remains below all blocks/cards/labels. It recalculates screen endpoints from both generation offsets and the outer scroll offset. Domain ranks and connection policy remain separate from rendering geometry.

A secondary click selects the node and opens its biography. Only hovering a tree node suppresses the native browser context menu through Flutter's browser API; leaving the node or disposing the editor restores the setting it changed. The rest of the page, including biography inputs, retains normal browser-menu behavior.

## Biography Forms

A narrow-screen biography is a full-screen route; a wide-screen biography is a side panel that reduces the canvas area. Selecting a relative navigates the main selection rather than duplicating the person model.

Read mode exposes parents, full/half siblings, children, facts, biography, and the album. In both read and edit views, facts precede the biography text. Fact chips and editors derive saturated, hue-preserving fills and contrasting accents from the existing stored palette; this is a UI treatment, not a color/schema migration. Editing is available only when the current session allows it. The relative editor can select an existing person or create one and then establish the requested parent/child relationship. Add Relative opens with **Новый человек** selected; **Из дерева** is the second source choice and is what reveals **Выбрать**. A new mother/father has its sex fixed by that role; the existing-person picker excludes known opposite-sex candidates but permits unknown sex without rewriting it. Occupied father/mother choices are disabled and use the theme's muted disabled text color in both themes, so they remain visibly distinct from available choices. An initial available parent/child relation kind is chosen. Both picker predicates and submission use the live role-specific parent slot: Add cannot replace an existing parent, including when a remote edit fills the slot while a picker, person creation, flush, or date write is pending. The existing-child route likewise cannot overwrite that child's occupied father/mother role. A person already created before a race remains a separate person; the UI reports failure rather than destructively rolling it back or replacing the newly arrived parent. Direct typed parent-field commands remain valid for explicit relationship editing outside Add. Child sex remains editable. There is no parental-role field: the focused person's live sex determines the link (female mother, male father); unknown sex retains the default father role without rewriting the person's sex. The role and edit permission are re-read after asynchronous creation/date writes before linking. Local cycle and item checks run again at the session command boundary.

The single **Брат/сестра** kind appears immediately before **Ребёнка** and always creates a new identity, with an editable sex field (unknown by default) and an optional birth date. The same source row stays visible, with **Новый человек** selected. **Из дерева** remains in that row but is muted and cannot be selected, and there is no graphical person picker. Stale picker callbacks cannot attach an existing person. One atomic `createSibling` command includes the new identity, initial name/sex/date and relationship. With both parents accepted it copies the pair and needs no direct edge; otherwise it joins the source's explicit sibling component. The form retains the attempted ID and retries the same event via flush after a saving failure, without orphan creation, a second link, or changing the locked target. Opening/canceling the form writes nothing.

Sex and relation-kind dropdowns expand within their field constraints; long labels are bounded rather than setting an intrinsic width that can overflow a phone dialog. A new child's birth date is optional, independently of the selected sex.

The death row keeps the date button and two explicit choices, **Жив** and **Не известно**. A stored death date shows the date and selects neither choice. **Жив** means no death date and life years end in **н.в.**; **Не известно** ends them in **?**. With neither choice stored, a birth date and no death still display as living, and both dates missing stay **?–?**. Choosing either state clears a death date. Choosing a date clears the explicit mark. Removing a death date records unknown rather than implying the person is alive. Read mode uses the same words.

The Add Relative form records the exact submitted child/parent-role/parent tuple. Its own matching optimistic edge is not displayed as an occupied-slot conflict while saving or during the closing route animation; a different remotely filled slot still is. Command-time slot, role, permission, and cycle checks remain strict. If that link's saving fails, the form keeps the visible error, locks the submitted target, and offers **Повторить сохранение**, which flushes the original immutable event rather than creating another link or overwriting a remote replacement.

Existing-person selection has one **Выбрать** (“Choose”) button, not an existing-person dropdown plus a second graphical picker. `TreeEditor` supplies the narrow `PickTreePerson` callback to the biography/dialog, avoiding a reverse dependency from forms to the canvas. A full-screen route reuses the complete tree with its layout, independent scrolling/zoom, trunk controls, and always-available search, starting at the current candidate or biography person.

Node taps, secondary taps, and search results only change the picker's focused person; they do not return early or open biographies. Ineligible nodes are dimmed but still browsable. A floating check button (`confirm-tree-person`) replaces the biography action and is disabled unless the current person satisfies the **live** predicate: person/focus still exist, role/sex compatibility, no cycle, and current edit permission. Pressing it rechecks eligibility and returns only the current focused ID. Cancellation preserves the dialog draft and the main canvas selection, zoom, and scroll state. Browsing, confirming, and canceling write no history. The dialog revalidates the returned ID, displays its name/years in the shared local name mode, and only its ordinary **Add** action writes the relationship.

Edit mode retains the relative list, with Add Relative directly below the **Родные** heading and before the parent/sibling/child groups. Explicit parent/child rows retain their edge-removal actions. Computed full and half sibling relationships remain navigable without an unlink action. Only an active **direct sibling edge** from the current person to that relative gets an edit-only X, with tooltip **Убрать прямую братскую связь**. Transitive component peers without a direct edge have no X. Removing that exact observed claim is immediate, without confirmation or parent writes; stale captured actions cannot unlink a replacement claim. A remaining shared parent therefore still establishes a half-sibling relationship after the direct component splits.

Setting or clearing a parent while a direct sibling component is active propagates through that component as model/session semantics, not a UI loop. Once both accepted parents are known, all current direct claims retire and the normal computed full-sibling block takes over; its sibling X controls disappear. A later parent clear does not resurrect retired direct links. Parent unlink still means a parent-role edit, so it propagates to all currently direct-linked siblings. Deletion, saving errors and retry remain explicit.

An edit-only Delete button replaces the old saving footer. It requires explicit confirmation, issues
one permanent person-deletion operation, and leaves other people intact. Failed optimistic deletion
can already hide the person; the biography must still expose its storage error and Retry, which flushes
the original immutable operation instead of issuing a second deletion. See [person deletion](tree-model.md#person-deletion-and-relationship-removal).

Surname controls use one personal atomic **Фамилия при рождении** field (`person-surname-field`) and the **склонять фамилию** checkbox. This field remains the birth configuration, independent of the current surname derived from marriage/change history. There is no **отдельная** toggle or shared editing scope. Every edit appends one `setSurname` operation with `scope: individual`, `familyKey: null`, targeting only that person. Their siblings are unaffected; descendants still follow normal canonical father inheritance.

An inherited field stays empty and shows the father's canonical base as a hint, plus the father's full name as its source. Historical shared-family values remain an explicit read-only fallback only until that person's first personal-register operation; clearing that field suppresses the legacy fallback and restores paternal inheritance. Opening or switching biographies never creates migration operations or copies inherited text. **склонять фамилию** defaults to true for a new/unset value and respects existing explicit/inherited false values. Its behavior remains literal `а`/`ы` suffixes, not grammatical inflection. Legacy family/maiden records stay in immutable history; no maiden control/caption/search alias is added. Remote values refresh the controller/checkbox without write loops; unchanged values preserve selection/IME state. Guests see formatted current names without editing controls. The inherited input and its father-source hint still use the canonical birth configuration rather than copying a later married surname. Saving errors use the biography's visible error/retry path.

Text controllers for name, biography, facts, and photo captions keep the `TreeTextSnapshot` associated with their visible value:

1. A local edit passes that base snapshot to `editTreeText()`.
2. The optimistic operation is applied before its first persistence await, so subsequent keystrokes reference their own inserted atoms. Its ID, payload, logical stamp, and UTC creation instant are fixed at that point; the author-prefix proof is assigned only inside the atomic store append and cannot change its text anchors.
3. A remote refresh maps selection and valid IME composition ranges to the new snapshot using stable character IDs and UTF-16 boundaries.
4. Removed facts/photos are not queried by still-mounted listeners while the parent rebuild is disposing their controllers.

Form closure is not saving. Each change immediately starts the normal authored-backlog append, whose browser writer lock/native queue can still be pending. The biography shows `session.saving` as local-saving progress, and asynchronous errors remain visible with retry even when an optimistic deletion hides the person. Retry flushes the same cores and resolves their canonical proofs; it does not resubmit replacement UI commands. Missing required Web Locks is a visible save failure, not a silent browser fallback. Selecting dates/sex/colors and moving list items issues typed operations rather than saving an entire stale form or array. The editor-only **This Is Me** action asks one brief confirmation question naming the person, with confirm/cancel buttons and no privilege or how-to prose; completion still uses only durable binding state. Releasing there enables another choice without rewriting history. Guests see neither the binding action nor the bound-profile caption, including when legacy history contains a guest binding. Promotion must be durable before the action or active person identity becomes available.

## Family and Surname History

**Фамилии и браки** sits immediately after the complete **Родные** section and before facts, in both biography modes. `PersonFamilyHistory` consumes `TreeDocument.historyOf(personId)` in domain order without its own sorting or duplicate marriage/surname rows. A real surname change has a large surname on the first line, with its known change date on the left; unchanged configurations have no first line. The second line is the custom reason or **Брак с** a clickable partner name in the shared live ИФ/ФИО mode. A deleted partner retains the explicit episode with **Удалённый человек**, without a navigation action.

Marriage date parentheses require a real start/end date or known lifelong death boundary. A common child's birth date is an ordering hint only and is never displayed as a marriage start. **Не известно** is the default end mode and renders `?` when a range is present. **Пожизненно** uses the first known death boundary, or `н.в.` only when both partners are explicitly alive; otherwise it says `пожизненно`. With no real date, even a lifelong choice adds no parentheses. Explicit dates are shared between partners; each partner's surname decision is independent.

Editors can add **Брак** or **Смена фамилии**, edit explicit/inferred rows, and remove a record after one short confirmation question. Guests can read and browse partners but receive no history commands. Marriage creation reuses **Новый человек / Из дерева**, the optional-DOB/name/sex fields, and the existing graphical-picker callback without importing the canvas. Existing candidates exclude self/deleted people but have no sex or ancestry-cycle restriction. Opening, picking, and canceling write nothing. A new partner can supply a canonical **Фамилия при рождении**; identity, sex, optional DOB and marriage are one atomic operation. **Менять фамилию** defaults on for women and off otherwise, snapshots a canonical partner surname rather than its rendered sex suffix, and uses the marriage start as the change date. The independent-change form supplies surname, date and custom reason. Both forms keep the existing 1970 date-picker default and full supported date range.

Form state owns drafts and the async command lifecycle. Pending submission disables duplicate commands, source/picker changes and dismissal. Editing dates and surname choice builds both operations before starting their optimistic appends, then awaits both; failed saving locks that submitted draft and retries existing immutable cores through `flush()`, even if a competing remote record has since won. The form tracks each frozen payload separately: if one command was rejected before append, Retry authors only that still-missing payload, never recreates an existing core, and closes only after all wanted operations have been appended and durably flushed. Failed optimistic removal retains a visible raw error and flush retry after the row disappears. Forms neither rewrite raw person-name/birth-surname fields nor expose an editable patronymic.

## Photo Input

The album uses `file_selector` as its platform boundary. It accepts PNG/JPEG/WebP, rejects input over 8 MiB, decodes with a portable codec, and uses Canvas/PictureRecorder resizing before PNG encoding. It avoids `ImageDescriptor.width`, which is unsupported in the tested web renderer. Results are at most 1024 px and 700 KiB.

Photos and captions are persisted through tree operations; selecting an avatar is an independent atomic field. The current avatar is bordered in the album. Decoding/processing and persistence errors are presented rather than silently discarding an upload. Images currently live in the immutable history, so deletion hides an item but does not free historical storage. See [storage limits](history-and-storage.md).

## Journal Presentation and Branding

`RoomChangesDialog` consumes the journal's author-topological order, with `(clock, id)` choosing among ready entries, then displays the groups in reverse order (latest journal groups first). It does not sort by displayed timestamps or editor names. Different actors can interleave even when they share a displayed person; one actor's durable successors cannot precede their predecessors in the underlying journal. Unproven optimistic drafts can acquire their final position when canonical proofs arrive, without changing payload or projection stamps.

The dialog groups **consecutive** tree operations only when issuing actor, person ID, and field key match. Intervening edits from another actor or field break the group. It shows the last operation's description/time for that group. This is view-level squashing: immutable operation IDs and deltas are not compacted or rewritten. An empty participant-alias operation is shown as **Имя не указано** (Name not specified); Anonymous remains a display fallback, not a replacement stored name. Disk connect/detach entries have readable **Яндекс Диск подключён / отвязан** descriptions rather than displaying raw binding JSON; credentials are never journal entries.

`createdAt` is an actual UTC epoch instant, not a monotonic journal counter. The formatter explicitly constructs `DateTime.fromMillisecondsSinceEpoch(..., isUtc: true).toLocal()`, then uses Flutter's locale date/time formatting. Device-clock corrections can make displayed times go backward; proof order is not wall time, and no clock agreement across devices is promised.

[tree_brand.dart](../../lib/ui/tree_brand.dart) supplies the shared tree mark and bounded loading/error surface. Animation honors reduced-motion settings. The initial HTML shell in [web/index.html](../../web/index.html) establishes mobile viewport/safe-area behavior before Flutter's first frame.

Theme roles are composed in `main.dart`; palette history and contrast are in [future-interface.md](../future-interface.md). The app's visible language is currently Russian; English UI names in documentation are translations, not a second localization layer.
