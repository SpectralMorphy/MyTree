# Yandex Disk Replica

[Architecture index](README.md) · [History and storage](history-and-storage.md) · [WebRTC synchronization](synchronization.md) · [User setup](../yandex-disk.md)

Yandex Disk is an optional second durable copy and an asynchronous exchange point for editors. Explicit Disk-enabled invitations also support first admission without another participant online, and an explicitly published binding folder supports anonymous read-only guest access. The local journal remains the persistence boundary and WebRTC continues live discovery/exchange. This page describes the implemented subset of the [future storage agreements](../future-storage-and-sync.md), not completion of their snapshot, attachment, or conflict-resolution proposals.

## Responsibilities

- [YandexDiskClient](../../lib/cloud/yandex_disk_client.dart) owns authenticated application-folder HTTP, explicit folder publication, anonymous public reads, paginated listing, immutable uploads, read-back confirmation, deadlines/body bounds, and sanitized errors. Its HTTP client can be substituted in tests. Small conditional [native/default](../../lib/cloud/yandex_http_stub.dart) and [browser](../../lib/cloud/yandex_http_web.dart) adapters isolate Fetch's referrer, cookie, redirect, and cancellation behavior.
- [RoomDiskSync](../../lib/cloud/room_disk_sync.dart) scans and validates batches, unions remote and local histories, uploads missing durable records, schedules retries/polling, and tracks acknowledgment of a frozen local history digest. In the same module, `readDiskRoomHistory()` reads a bounded admission snapshot without writes; `RoomDiskReadSync` polls public history for guests without upload or acknowledgment of their local edits. None of these components authors operations or grants membership.
- [RoomDiskRetirements](../../lib/cloud/room_disk_retirements.dart) reconstructs and owns independent final-detach deliveries for old bindings, each with an archived credential, frozen predecessor-complete history cutoff, and its own `RoomDiskSync`. Replacement of the active binding does not cancel that queue.
- [DiskBinding](../../lib/cloud/disk_binding.dart) projects public connect/detach history into the active binding identity and owner actor. It contains no token.
- [RoomSession](../../lib/room_session.dart) checks durable editor/owner permissions, prepares consented invitations/publication, validates and persists Disk admission before membership, composes cloud work with the existing serialized history-merge queue, retains detach retries, and transfers credentials over ordinary negotiated editor RTC channels.
- [DiskCredentialExchange](../../lib/cloud/disk_credential_exchange.dart) owns the additional editor-only rendezvous peer/channel lifecycle and bounded credential handshake, enabled only when the ordinary ready room host is a guest. It never authors history or grants membership.
- [RoomStore](../../lib/storage/room_store.dart) persists editor credentials and a separate current public-access pointer outside the operation journal; [room dialogs](../../lib/ui/room_dialogs.dart) collect the token, editor-sharing consent, and guest-publication consent. [RoomDiskAccess](../../lib/room_identity.dart) defines the strict invitation envelope and shared public-share URL validator. Local saving, peer readiness, Disk-read readiness, and cloud-copy acknowledgment remain separate facts.

## Local-first flow and immutable layout

An edit follows the existing optimistic/atomic-authored/local-durability path. Disk reads only canonical durable history. A cloud outage does not roll back an edit, replace local data with an empty document, or prevent further local work. The local journal is also the durable retry source: no tab-close handler is needed to construct an upload queue.

Files are application-folder resources, private unless their binding folder is explicitly published for guest access:

```text
app:/mytree/<roomId>/<bindingId>/batches/<sha256>.json
```

`bindingId` is the immutable connect operation ID. Each JSON batch has `v: 1`, `roomId`, `bindingId`, and a `history` list containing the existing complete `RoomEdit` envelopes/proofs. Its filename is the lowercase SHA-256 of its actual UTF-8 bytes. Uploads use `overwrite=false`; an existing name is accepted only after confirming identical bytes. There is no shared mutable `tree.json`, manifest overwrite, or cloud compare-and-swap requirement.

A synchronization round:

1. Enumerates the entire batches directory, following every listing page rather than treating the first page as the complete cloud history.
2. Reads uncached batches and checks filename/hash, room and binding identity, record syntax, and immutable-ID conflicts. Unchanged content-addressed batches can be reused from the in-memory cache.
3. Unions remote records with the current durable local journal and validates the existing author predecessor/base proofs across that union before merging through the normal local persistence boundary. An individual file need not contain every predecessor: a partially uploaded sequence can be repaired from records retained locally, but an incomplete resulting author prefix cannot be accepted.
4. Compares durable local history with the scanned cloud inventory and uploads missing records in immutable batches. Reloading or retrying reconstructs this difference from local history and a fresh full cloud scan, including after a partially completed upload.
5. Records acknowledgment only for the frozen local set covered by confirmed cloud files. Edits made during the round remain pending until a later round; acknowledgment does not prove that no offline participant has an unseen tail.

Local changes schedule cloud work; periodic scans and manual synchronization also pick up another editor's files. Editors with a retained valid credential can exchange changes asynchronously without overlapping online sessions. A plain ID or legacy/role-only invitation still needs ordinary online admission. A Disk-enabled invitation instead supplies a validated-history admission route; guests can retain public access and poll it without an editor token.

## Offline-capable invitations, publication, and admission

“Offline-capable” means **no other participant must be online**, not that Yandex Disk works without Internet. The invitation includes the room ID, requested role, and optional active-binding access. Editor access carries `{v: 1, bindingId, token}`; guest access carries `{v: 1, bindingId, publicUrl}`. Web payloads remain entirely in the URL fragment as base64url UTF-8 JSON; native/copy-code JSON nests the access under `disk`. Role/access mismatch, invalid/oversized payloads, mixed/unknown access fields, and repeated security keys are rejected without falling back to an ID-only invitation. See the [identity contract](rooms-and-identity.md#invitations) for bounds and legacy compatibility.

`prepareDiskInvitation()` rechecks the active binding and durable roles/credentials around asynchronous work. Editor-token sharing requires explicit consent and returns only that binding's stored credential; it never publishes a folder. For guests it first reuses a valid matching public-access pointer, allowing a guest to forward existing read access. First publication requires an explicit durable editor and separate UI consent that the **whole history, including deleted records**, becomes readable. Before publication the session flushes local history, synchronizes, and checks acknowledgment of the current durable set. It publishes only `app:/mytree/<roomId>/<bindingId>`, never `app:/mytree` or another tree. The client confirms publication from directory metadata and validates the returned share URL before it is stored/returned. Failure after provider publication is not guaranteed rollback: the folder may already be public even if the subsequent local save fails.

`readDiskRoomHistory()` performs no directory creation, publication, upload, journal merge, or membership write. It reads all candidate batches, with one absolute deadline propagated through pagination and download-link/transfer requests, at most 2048 candidates, an 8 MiB aggregate download, an 8 MiB canonical local/cloud union, and 8 MiB individual private/public response caps while streaming. Repeated listing identities invalidate an overlapping scan instead of being silently deduplicated; cancellation/deadline checks prevent starting subsequent pages or transfer subrequests. Names must be content-addressed SHA-256 JSON filenames before constructing paths. It checks hash/bytes, room/binding envelopes, immutable-ID conflicts, and complete author predecessor/base closure across cloud plus retained local history. The invited binding must still be active after union; a known detach/replacement cannot be ignored to accept stale access. Session admission additionally requires the active binding's owner to have an **explicit editor role in validated history**, not merely the legacy implicit-editor default. These are structural trusted-client checks, not signatures or proof against a malicious author.

The session serializes this work with admission/history merges before starting RTC or write-capable replication. It validates first, imports/flushes history, authors and durably saves the local profile/initial role, retains only role-permitted access, and flushes before **committing membership last**. A validated explicit editor invitation can promote an existing guest; its editor role must be durable before the matching editor token is retained. Ordinary guest restore/public access cannot promote a guest or retain an editor token. Cancellation, stale attempts, and binding/role changes are rechecked around writes. Failure can leave already durable records/access for retry, not a cross-record rollback or automatic membership. Read/save errors remain sanitized and visible; retry or ordinary online admission remains possible.

Verified Disk admission opens the room with `История загружена с Диска · онлайн-сверка продолжается`. It does **not** set a peer ACK, settle a live cohort, or furnish local-tab protocol proof. RTC discovery and its unchanged checkpoint exchange continue independently. Neither a successful read nor cloud-copy acknowledgment proves the newest global state: another offline editor can have unseen history.

A joined guest with matching retained public access uses `RoomDiskReadSync` for bounded periodic reads (30-second default) and resume-triggered refreshes, merging validated updates through normal local persistence. It makes no private API call, creates no cloud files, and never uploads guest alias/history changes or claims their cloud durability. An established public guest may also import its exact binding's validated final disconnect together with preceding final edits, then stops polling that pointer. The same terminal snapshot can finish a saved accepted guest's reload when its retained local binding matched before the read; it cannot admit a fresh guest, grant another binding, or change private editor retirement behavior. Other binding/role mismatches stop use of the pointer. Its status is “history read,” not “copy confirmed”; ordinary WebRTC can still exchange guest metadata. Public access is stored separately from editor credentials and never becomes a room operation.

## Acknowledgment and failures

An upload link, completed HTTP send, or HTTP `202 Accepted` is not cloud durability evidence. The client reads back the actual remote bytes and compares them with the intended upload, with bounded confirmation retries. Existing-file conflicts also require byte equality. API/transport timeouts and failed confirmation remain failures, not successful copies.

Authenticated API requests and upload PUTs reject redirects. Only anonymous signed-download GETs follow redirects: Disk normally redirects downloads to a storage host. Initial signed URLs and the final response URL exposed by the production transports must match the HTTPS/443 Yandex-domain allowlist, with no userinfo or fragment; unexpected final destinations are rejected before consuming the response body. OAuth is sent only to the fixed API endpoint, never to a transfer URL. On web, a scoped Fetch adapter uses `referrerPolicy: no-referrer` and `credentials: omit`: the observed Disk download hosts reject requests carrying the application's Referer with HTTP 403 lacking CORS headers. This does not change the application's global referrer policy or disable CORS. Fetch follows redirects using its browser-defined hop cap; it does not expose intermediate destinations or honor the native client's five-hop setting. Redirects therefore carry no OAuth, cookies, application referrer, or request body; final URL checks and batch/content verification remain mandatory. Each request is abortable: deadline expiry cancels Fetch/native I/O rather than leaving a timed-out body buffering in the background. Closing the owned HTTP client also aborts its pending requests.

The cloud coordinator keeps a digest of the local set acknowledged by successful listing/download/upload confirmation. **Копия на Диске подтверждена** applies to that current known durable set, not global consensus, an independent backup retention policy, or the local/WebRTC saving indicator. A changed local digest invalidates that positive status. Error text is sanitized: response bodies, signed download/upload URLs, authorization headers, and raw platform exceptions must not enter UI or diagnostics.

## Binding, ownership, and offline races

The journal stores `kind: diskConnection` with JSON in `text`: `{action: connect}` or `{action: disconnect, bindingId: ...}`. The token and remote file contents never enter these operations. Binding projection replays connect/detach records in deterministic `(clock, id)` order: the first available connect remains active until a detach referencing that exact binding ID. A detach cannot remove a later replacement binding.

Only an editor can connect when there is no active binding. Disconnect is available to the original owner actor, or another editor actively bound to the same durable tree person as that owner. A shared person is a trusted-client ownership convenience, not a merge of actor journals or credentials. Guests have no editor token, Disk write/connect/unlink/manual-sync commands, or **This Is Me** binding rights; retained public access permits read-only polling and forwarding guest invitations.

Two disconnected editors can both connect before learning of each other. Their local command guards are not a global lock. On union, deterministic replay chooses the surviving connect; a later arrival may change the projected winner. Ignored claims remain in immutable history, but a later claim does not simply replace an active one. No atomic cross-device reservation or globally serialized connection is promised.

### Independent detach retirement

Disconnect first persists the exact detach in the local journal. `RoomDiskRetirements` retains a separate delivery for that old binding: its archived credential, an independent `RoomDiskSync`, and a frozen predecessor-complete eligible history prefix. It first validates the full canonical history, then walks author-topological order, including only records at or before the detach's `(clock, id)` cutoff whose `authorPrevious` and sealed `authorBase` are already included. An old-clock draft that acquired a post-cutoff predecessor during late persistence is **excluded**, not recursively expanded into newer-binding data. If the detach itself cannot fit this closed prefix, retirement reports a visible queue error and starts no retired upload. Later active-binding edits must not leak to the old directory.

On restart or history refresh, the retirement coordinator scans historical disconnects, resolves their binding-scoped credentials, and reconstructs those frozen deliveries. A new active binding B does not reconfigure or cancel retirement A. The active replica and each retirement share the session-owned HTTP adapter with child disposal explicitly not closing it; disposing one finished retirement must not break another replica's HTTP work.

Once no binding is active, an eligible editor may connect a replacement **without waiting for old retirements to succeed**. An expired/revoked old token or failed old provider must not deadlock replacement setup. This permission does not erase or acknowledge the old queue: offline/error retries and pending-retirement status remain independent, including when the new active copy succeeds. Only read-back acknowledgment of an old delivery's frozen set permits binding-scoped removal of its credential and retirement entry; cleanup must preserve the new binding's archive/pointer. A locally saved detach or a newly connected Disk is not confirmation of the old final upload.

Unlinking does not delete cloud files, unpublish a previously shared folder, revoke OAuth, or remotely erase token/link copies. OAuth revocation and removal of public sharing must be performed separately in Yandex account/application or folder settings. Token revocation stops copies using that grant; it is not revocation of an existing anonymous public link.

## Credentials and the trust boundary

There is no configured OAuth client ID or in-app browser authorization/token-issuance flow. The owner supplies an externally obtained token with `cloud_api:disk.app_folder` access. A personal owner account is supported without a broker or a mandatory separate account. Application-folder scope is **application-wide, not per tree**: sharing the token can expose other room subdirectories accessible to that OAuth application. Explicit guest publication shares only the chosen binding folder; it is not implicit publication at connect, entry, or invitation-dialog rendering time.

Credentials are versioned local metadata associated with a room and binding ID, stored separately in browser `localStorage` or native JSON sidecars. Binding-scoped archives are written before a compatible latest pointer, so concurrent staged connects or a newer pointer cannot overwrite the only credential retained for another binding's final-detach retry. Scoped cleanup removes only the targeted binding and any matching pointer; full room-credential cleanup is a separate operation. Guest public access has its own current pointer without credential archives. See the [storage contract](history-and-storage.md#separate-local-disk-credentials). Both are **plaintext**, not an OS credential vault or encrypted storage. Editor tokens are excluded from the journal/exports, public build values, cloud batches, and guest invitations. They enter editor invitation URL/QR/code payloads only after explicit sharing consent. Anyone able to read that invitation, local application storage, or a running editor client may obtain the token. Base64url and fragment placement do not protect it from the recipient, clipboard, screenshots, or browser extensions.

The normal room path retains the separate `diskCredentials` RTC message with empty history and an exact binding identity, negotiated by `diskSync`. Sending/receiving requires explicit durable editor roles and a matching active binding; guest hubs must never receive or relay the secret.

Only when an editor's ordinary live, **ready host is durably a guest** does `RoomSession` enable `DiskCredentialExchange` for the joined network-owning editor tab. The helper registers an editor-specific rendezvous alias, connects only exact known durable-editor aliases, and uses its bounded `diskHello` / `diskAccess` handshake over direct RTC channels. The active binding is rechecked before accepting/persisting credentials. It stops its peer/channels when that fallback condition no longer holds; it is not a permanent parallel mesh or a replacement for normal negotiated `diskCredentials` delivery. This does not make the guest a credential broker. Local tab state messages and the public signaling channel are not token transports.

WebRTC protects transport, but room roles and actor/person claims still assume trusted family clients. Author proofs and SHA-256 content names detect structural disagreement; they are not signatures or cryptographic authorization. An editor can copy a token, and a modified client is outside the role model's security guarantee.

## Unchanged limits and remaining scope

- The full-history/transfer budget remains 8 MiB, including accumulated historical operations; cloud batching is not journal compaction or an unlimited archive.
- Photos remain inline data URLs in immutable tree history. PNG/JPEG/WebP processing limits remain 8 MiB input, at most 1024 px, and 700 KiB processed payload. Deleting a photo does not reclaim its historical bytes.
- No snapshots, separate attachment object store, history garbage collection, OAuth broker, or cryptographic membership system is introduced. Public guest access exposes existing immutable history, not a redacted current-tree snapshot.
- Provider account setup, token issuance, real-account upload behavior, browser CORS, quotas, and revocation require their own operational checks. A description of implemented code is not a claim that a live Yandex account was exercised in this development session.
